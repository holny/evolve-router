# 价格分层路由方案（Price-Tier Routing Proposal）

> 状态：**已实现**（2026-10-14）：S1 成本模型 ✅ · S2 价格层硬闸 ✅ · S4 缓存经济 ✅ · S5 比例控制器 ✅ · S6 观测 ✅ · **S7 回测验收 ✅**（`evo-router report` / `GET /api/report`）
> 实现位置：`provider_info.rs`(价目/峰谷) · `scoring.rs`(est_cost) · `engine.rs`(tier 硬闸/暖缓存粘性) · `ratio.rs`(比例控制器) · `tags.rs`(模型标签) · `calibration.rs`(难度校准)
> 目标：让"任务难度分布 7:2:1"真正映射为"请求次数 7:2:1"——多用便宜模型、少用昂贵模型；同时按**供给侧**差异（配额型 vs 付费型）决定使用倾向，且不误伤"便宜但能力强"的模型。

---

## 0 地基：DeepSeek 计价文档的硬事实

来源：<https://api-docs.deepseek.com/zh-cn/quick_start/pricing>（2026-10 版）

| 项目（元 / 1M tokens） | deepseek-flash | deepseek-v4-pro | 倍率 |
|---|---|---|---|
| 输入·**缓存命中**（空闲 / 高峰） | 0.02 / 0.04 | 0.15 / 0.30 | ~7.5× |
| 输入·**未命中**（空闲 / 高峰） | 1 / 2 | 4.5 / 9.0 | 4.5× |
| 输出（空闲 / 高峰） | 4 / 8 | 13.5 / 27 | 3.4× |
| 并发 | 2500 | 500 | — |

**两条统治性结论**：
1. **缓存命中 vs 未命中 ≈ 50×（flash）/ 30×（pro）**——前缀缓存是成本的第一变量，比"选哪个模型"影响更大；
2. **峰谷时段半价**（北京时间周一至周五 9:00–12:00、14:00–18:00 为高峰，其余含周末/法定节假日为空闲）——有效成本必须含时钟系数。

## 1 决策的两个正交维度

本方案的核心结构：**能力维（任务要求）× 供给维（钱怎么付）**。

```
                 能力维（难度→必须达到的质量）
                          ▲
   L3 困难（10%）─────────│───────────── 全能力层可选
   L2 一般（20%）─────────│─────── cheap + standard
   L1 简单（70%）─────────│─ cheap
                          └──────────────────────────────▶ 供给维（钱怎么付）
                     配额型（会过期）      付费型（真金白银·不过期）
                     优先使用 ↑            尽量少用 ↓
```

- **能力维**决定"这个任务至少要多强的模型"（质量门槛 + 价格层上限，见 §2）；
- **供给维**决定"同等能力下先花哪份钱"（配额优先/临期优先，见 §3）；
- 两者独立：一个 L3 任务若配额池里有达标模型，就绝不动付费余额。

## 2 能力维：难度分层 → 价格层映射（7:2:1 目标）

### 2.1 难度三级（复用现有 L1~L4 判定，合并为三档）

| 难度档 | 现判定对应 | 目标占比 | 允许的价格层（硬闸上限） |
|---|---|---|---|
| 简单 L1 | difficulty ≤ 0.8 | **70%** | 仅 cheap |
| 一般 L2 | 0.8 < d ≤ 2.0 | **20%** | cheap + standard |
| 困难 L3 | d > 2.0 | **10%** | 全层（含 premium） |

### 2.2 价格层不看名字、只看有效成本

`cheap / standard / premium` 按**典型流量配比下的每百万 token 综合有效成本**在**候选集内分位**切分（p50 / p80），而非绝对价。

### 2.3 关键规则（硬化）

1. **premium 默认只服务 L3（10%）**；
2. L1/L2 使用 premium 的唯一出口是**成本倒挂**：`premium.effective_cost ≤ standard 池中位数`（官方定价同价/更便宜、活动价、订阅内）→ 放开；
3. **tier 闸只做上限，不做下限**——`glm-5.3-flash` 这类"便宜层但跨家族能力更强"的模型，在 L3 依然可凭质量分赢过别家 pro；名字带 pro 的贵模型不会因名字获得资格；
4. 质量门槛继续用现有 `quality_floor`，与 tier 闸是**两道独立门**。

## 3 供给维：配额型 vs 付费型（使用倾向差异）

### 3.1 语义二分

| | 配额型（订阅套餐 / coding plan） | 付费型（按量 API） |
|---|---|---|
| 成本本质 | 已预付；**边际成本 ≈ 0** | 真金白银，逐次扣费 |
| 过期性 | **窗口到期即作废**（5h/周/月重置） | **不过期**（余额长期有效；赠送余额若有到期日另算，先按不过期） |
| 心理成本 | 用不掉才亏 | **花起来心疼** |
| 使用倾向 | **优先消耗**（早用早省，尤其临期） | **尽量少用**（兜底 / 能力刚需） |

### 3.2 三条供给规则

**R1 配额优先（同能力层内）**：配额型额度未耗尽的模型，排序优先于付费型——因为 mp≈0；付费型只在①配额池全部耗尽/冷却，或②配额池无满足质量门槛者时启用。

**R2 临期紧迫度（用不完就是浪费）**：

```
urgency(pk) = f(剩余额度比例, 距离重置时间)
  · 剩余多 + 重置临近（用不完） → 强正加成：尽快用掉，哪怕低难度任务也给它
  · 剩余少 + 重置还远（紧张）   → 负加成：节约使用，留给高难度任务
  · 示例：剩余 ≥60% 且 ≤1h 重置 → +强势；剩余 ≤20% 且 >6h 重置 → −惩罚
```

这条把"配额过期作废"从口号变成可计算的排序项；同时避免"月初烧光、月底没得用"。

**R3 付费型惩罚（钱不过期，所以更值钱）**：

```
score' = score + quota_bonus(配额型) + urgency(pk) − payg_penalty(付费型)
payg_penalty 固定基线（如 −8%）+ 可选随"当日付费消耗速度"上调
```

付费型仍可凭**能力刚需**（L3 且配额池不达标）或**价格倒挂**（付费型单价 ≤ 配额型等效机会成本）胜出。

### 3.3 与 7:2:1 的关系（口径说明）

- 7:2:1 约束的是**能力维**（任务难度分布 → 质量层分布）；
- **供给维**决定"谁来承接这些请求"：理想状态是配额型承接绝大部分（含高难度），付费型只兜"配额耗尽/能力不足"的尾巴；
- 若用户**只有付费型**：7:2:1 直接体现为"70% 请求走便宜模型"；
- 若用户**配额型为主**：则体现为"配额池优先吃满 + 付费尾巴极短"，并另设 KPI 看**配额利用率**而非金额。

### 3.4 配额型的等效单价（供跨供给比较）

订阅套餐拿不到真金额时，用**等效单价**参与第 2 节的价格分层：

```
等效单价 = 套餐月费 / 窗口额度（或 / 额度 × 官方折算系数）
  例：zhipu coding plan 月费 ÷ 月 credits；opencode-go 订阅价 ÷ 月度美元额度
```
等效单价通常远低于同能力付费型 → 在能力达标前提下，配额型天然获得"便宜"标签并优先。

## 4 有效成本公式（含缓存与峰谷）

```
effective_cost(m, session, now)
  = [ in_miss_price × (1 − hit_rate_est) + in_hit_price × hit_rate_est ] × prompt_weight
  + out_price × output_weight
  × peak_factor(m.vendor_timezone, now)              // DeepSeek: 0.5 空闲 / 1.0 高峰
  + cache_write_cost（有此计价的 provider）
```

- `hit_rate_est`：该会话前缀的实测命中率（relay 已在记 `cached_tokens / prompt_tokens`，取滑动均值）；
- **切换模型的缓存惩罚**：同会话切模型 → 前缀全 miss，切一次代价 ≈ `前缀规模 × (新模型 miss 价 − 旧模型 hit 价)`。若该代价 > 单价差收益，**不切**——哪怕新模型列表价更便宜；
- sticky"暖缓存不切"条件：`cache_hit_p50 > 阈值 ∧ 圈数未耗尽 ∧ 新候选在允许层内 ∧ 预估节省 < 重打前缀成本`。

## 5 7:2:1 的达成机制（比例反馈控制器）

单请求决策无法保证分布，增加**滑动窗口比例控制器**（复用 explore_ratio 思路，不引入新随机源）：

- 统计最近 N = 200 次：各价格层 / 各供给类型的占比；
- 目标（可配）：
  - 能力层 `[cheap 70%, standard 20%, premium 10%]`（±5pp）；
  - 供给层（若存在配额型）`配额型 ≥ 80%`（不足说明配额没吃满 → 提示/纠偏）；
- 超出目标 → 对应因子乘软惩罚（1.2~1.5）；不足 → 取消惩罚；
- 作用：**难度判定偏松/偏严或供给倾斜时，由实际消耗分布反向压回**。

## 6 叠加顺序（最终决策链）

```
① 配额闸门（已实现：窗口满/429 → 出局；API 型 90s 官方复核；无 API 型 5–10min 真实探活）
② 能力维：难度 → 质量门槛（quality_floor）+ 价格层上限（tier 硬闸 + 倒挂例外）
③ 供给维：配额型优先 → 临期紧迫度加成 → 付费型惩罚
④ 成本模型：有效成本（缓存命中率 × 峰谷时段）× 比例控制器的软惩罚
⑤ 评分排序（quality / speed / cost / stability / headroom）+ sticky 暖缓存不切
```

## 7 落地清单（改动量从小到大）

| 步骤 | 内容 | 位置 |
|---|---|---|
| S1 | **成本模型统一**：散装 `model_rates` → `CostModel { in_miss, in_hit, out, currency, peak_windows }`（先落 deepseek / zhipu / opencode 官方口径） | `plans.rs` |
| S2 | **价格分层**：候选集内 p50/p80 分位 → `m.price_tier`；配额型按等效单价参与 | `scoring.rs` |
| S3 | **tier 硬闸**：`difficulty → max_tier` + 倒挂例外 | `engine.rs` |
| S4 | **供给维**：配额优先排序 + 临期紧迫度 + 付费惩罚（数据源：plan_budgets / quota observed） | `engine.rs` + `scoring.rs` |
| S5 | **缓存经济**：`hit_rate_est` 进成本因子；sticky 暖缓存不切 | `scoring.rs` + `engine.rs` |
| S6 | **比例控制器**：能力层 + 供给层双目标 | flywheel 记忆 + `engine` |
| S7 | **可观测**：events 记 `difficulty / price_tier / supply_kind / effective_cost / urgency / cache_ratio`；`/api/stats` 出分布直方图与**配额利用率/浪费率** | `relay.rs` + `meta.rs` + 面板 |
| S8 | **回测验收**：events 回放分布报告 | `evolve-memory::backtest` |

### 验收 KPI
1. L1 使用 premium 比例 ≈ 0；
2. 能力层分布 ≈ 7:2:1（±5pp）；
3. **配额利用率**提升（临期浪费率 = 重置时剩余 < X% 的窗口占比 下降）；
4. 付费金额/请求 相对基线下降 ≥ X%（仅有付费型时体现为便宜模型占比）；
5. 会话切模型率下降、缓存命中率上升；
6. 质量不退化（成功率/失败率不劣化）。

### 配置开关（灰度 / 回滚）
`price_tier_gate`、`ratio_target`、`supply_preference`（配额优先开关）、`urgency_enabled`、`payg_penalty`、`cache_aware`、`peak_aware`、`inversion_exception`。

## 8 风险与对策

| 风险 | 对策 |
|---|---|
| 难度判定偏松 → 总用贵模型 | 比例控制器纠偏 + 判定侧回测校准 |
| "便宜 = 弱"误判（flash > 别家 pro） | tier 只做上限；跨家族能力分（benchmark + 实测 bias + 飞轮） |
| 配额临期抢跑（月初烧光） | R2 双向：紧张时负加成（留给高难度）、临期时正加成（避免浪费） |
| 付费余额有到期日（赠送余额） | 先按不过期；若数据可得则并入 urgency |
| 缓存命中率估计误差 / 冷启动必 miss | 首次按 miss 计价；实测命中率滚动修正 |
| 峰谷时段跨厂商时区复杂 | 先接 DeepSeek，其余单档价 |
| 订阅等效单价难算（额度口径不一） | 用"窗口额度 × 官方折算系数"近似；缺数据则该 provider 只参与供给维不参与价格分层 |

## 10 待拍板问题

1. **分位阈值**：候选集内 p50/p80 切 cheap/standard/premium，还是绝对价阈值（如 ¥2 / ¥6 每 1M 综合）？
2. **容忍带与窗口**：7:2:1 ± 5pp、N=200 是否合适？
3. **倒挂判定**：`premium ≤ standard 池中位` 还是更严格（≤ 池 25 分位）？
4. **供给偏好强度**：配额优先加成 / 付费惩罚各给多少？（建议先 −8% 付费惩罚、配额 +5%）
5. **临期紧迫度阈值**：剩余 ≥60% 且 ≤1h 重置 = 强加成；剩余 ≤20% 且 >6h = 负加成——是否认可？
6. **配额利用率 KPI**："浪费"定义（重置时剩余 < 20% 算浪费？）与目标值？
7. **落地顺序**：建议 S1→S2→S3（最小闭环）→ S4 供给维 → S5 缓存经济 → S6 控制器 → S7/S8 观测与验收，是否认可？
